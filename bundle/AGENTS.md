## الفلسفة: Spec-Driven Development

**لا يُكتب أي كود لميزة جديدة بدون Spec معتمد.** نبدأ دائمًا بالمواصفات، ثم التخطيط، ثم المهام، ثم التنفيذ، ثم الاختبار، ثم تحديث الـ Spec.

```
1. Spec     →  /speckit.specify [وصف الميزة]   (spec-architect)
2. Clarify  →  /speckit.clarify                 (spec-architect)
3. Plan     →  /speckit.plan                    (spec-architect + architect)
4. Tasks    →  /speckit.tasks                   (spec-architect)
5. Design   →  UI/UX + Architecture             (designer + architect)
6. Build    →  Frontend + Backend               (frontend + backend)
7. Test     →  Unit + Integration + E2E         (tester)
8. Security →  Threat model + Pen test          (security)
9. Deploy   →  CI/CD + Infra                    (devops)
10. Update  →  Mark Spec "Completed" + Changelog (spec-architect)
```

| **devops** | مهندس DevOps — Docker، CI/CD، النشر، المراقبة | subagent |
| **bug-hunt** | مدقّق أمني عدائي — ثغرات، تهديدات، تتبع source-to-sink | subagent |

| **implementer** | منفّذ مهام الكود — يبني الميزات بجودة عالية مع اختبارات | subagent |

## قواعد إلزامية

1. **لا كود بدون Spec** — لكل ميزة جديدة أو تغيير كبير.
2. **Spec قبل التنفيذ** — ابدأ بـ `/speckit.specify` دائمًا.
3. **اختبارات إلزامية** — لا مهمة تكتمل بدون اختبارات ناجحة.
4. **الأمان أولاً** — راجع كل ميزة حساسة مع `security`.
5. **التزم بالبنية** — لا تكسر AGENTS.md المحلي أو الـ conventions.
6. **وثّق القرارات** — كل قرار معماري في `decisions/ADR-*.md`.
7. **حدّث الـ Spec** — عند الانتهاء، ضع "Status: Completed" + Changelog.
8. **الرؤية والتحقق البصري يُفوّضان تلقائيًا** — أي مهمة تتضمن صورة **أو تحققًا بصريًا من واجهة** تُحال فورًا إلى `vision` بدون سؤال.
9. **حسابات الاختبار تُحذف فورًا بعد الانتهاء (قاعدة إلزامية — قرار المالك 2026-09-09):** أي حساب اختبار (Test user/trainee/specialist) أو بيانات وهمية تنشأها أثناء العمل **يجب حذفه نهائيًا من قاعدة البيانات فور انتهاء المهمة** — مع بياناته التابعة (assignments, tasks, evidence, ...). لا يُسمح بترك أي حسابات اختبار في الإنتاج تحت أي ظرف. المحصلة النهائية: قاعدة بيانات نظيفة تمامًا من حسابات التيست.
10. **ممنوع تغيير بيانات المستخدمين الحقيقيين من تلقاء نفسك (قاعدة إلزامية — قرار المالك 2026-09-11):** أي تعديل على بيانات مستخدم حقيقي (إعدادات، مواعيد، مستويات، مهام، حجوزات، اشتراكات) **يتطلب إذنًا صريحًا من المالك أولًا** — تعرض المقترح وتنتظر الموافقة، ولا تنفذ أبدًا بمبادرة ذاتية حتى لو بدا التعديل "مفيدًا". الاستثناء الوحيد: تنفيذ اختيار المستخدم نفسه المنقول عبر المالك حرفيًا.

## 🔀 التوجيه التلقائي: الرؤية + التحقق البصري من الواجهات (Vision & UI-QA Auto-Routing)

**القاعدة:** أي agent (أساسي أو فرعي) يقابل واحدة من هذه يحوّلها **فورًا** إلى `vision` subagent عبر أداة `task` **بدون أن يطلب إذنًا من المستخدم**:

1. **رؤية صورة:** ملف صورة على القرص (`.png .jpg .jpeg .webp .gif`)، أو طلب "انظر/حلل/اقرأ هذه الصورة/اللقطة/المخطط/التصميم".
2. **التحقق البصري من واجهة (UI-QA):** سؤال مثل "هل ظهرت الميزة X في الواجهة؟"، "تأكد التعديل باين صح؟"، مراجعة شكل صفحة/مكوّن/زر/نموذج بعد تنفيذه أو تعديله، فحص التجاوب (responsive) — أي **حكم على ما يجب أن يظهر** وليس على ما يحدث خلف الكواليس.

### حدود النطاق — من يأخذ ماذا؟
| نوع الفحص | الـ agent المسؤول |
|---|---|
| شكل الميزة/العنصر في الواجهة، موضعه، نصوصه، تجاوبه | **`vision`** (وضع UI-QA: لقطة + مقارنة بالمواصفة + PASS/FAIL) |
| منطق، APIs، تكامل، اختبارات كود (unit/integration/e2e) | `tester` |
| ثغرات، صلاحيات، تهديدات، pentest | `security` / `bug-hunt` |
| استعلامات/schemas/سلامة بيانات | `database` |

`vision` **يرفض بأدب** أي فحص غير بصري ويحوّله للجهة المناسبة — لا تدفعه لاختبار أمن أو باك-إند.

### لماذا تلقائي؟
النموذج الرئيسي قد لا يدعم الرؤية. الـ `vision` agent مربوط بمجموعة `pool3/role/vision` على الجيتواي، وهي توفّر **توجيهًا تسلسليًا مجانيًا أولًا**:
1. **المجاني أولًا:** `deepseek-v4-flash-vision-exp` (B.AI) — يُجرَّب دائمًا أولًا.
2. **المدفوع عند الحاجة:** لو المجاني غير متاح (429/403/5xx بعد المحاولات)، ينتقل تلقائيًا إلى `role/vision-paid` (Claude Opus 5 عبر 3 لوحات).
3. **خط دفاع أخير:** `role/deep → role/code`.

لا يحتاج الـ agent ولا المستخدم أي تدخّل — الجيتواي يقرّر، والمجاني يُفضَّل دائمًا.

### متى تُعالج محليًا بدون إحالة
- إذا كان **نموذجك الحالي نفسه يدعم الرؤية** والمستخدم أرفق الصورة مباشرة داخل المحادثة، يكفي تحليلها محليًا.
- لكن **أي ملف صورة على القرص أو لقطة UI** تذهب إلى `vision` دائمًا، حتى لو كان نموذجك بصريًا — للفصل ولتوفير التوجيه التسلسلي.

### صيغة الإحالة
```
# تحليل صورة
task(subagent_type="vision", prompt="حلل الصورة بهذا المسار <PATH> وأجب عن: <السؤال>")

# تحقق بصري من ميزة في واجهة (UI-QA)
task(subagent_type="vision", prompt="تحقق بصريًا من الميزة '<الوصف>' على <URL أو file://path>. المتوقع: <نقاط المواصفة>. صوّر سطح المكتب والموبايل وأصدر PASS/FAIL بجدول الأدلة.")
```

### متى تُصوّر صفحة محلية؟
- صفحة ثابتة: `file:///absolute/path.html` مباشرة.
- تطبيق يعمل: تأكد أن السيرفر/dev-server يعمل قبل الإحالة (أنت من يشغّله إن لزم — `vision` نفسه لا يرفع سيرفرات).
- صفحات تتطلب دخولًا: الـ screenshot الآلي لا يسجّل دخول؛ استخدم صفحة تجريبية أو سلّم الأمر لـ `tester` لاختبار E2E كامل.

## الصلاحيات

**كل الأدوات مسموحة تلقائيًا (auto-approve).** OpenCode يعمل بدون طلب إذن في أي شيء — تنفيذ أوامر، تعديل ملفات، تشغيل اختبارات، نشر. هذا الإعداد للإنتاجية القصوى في بناء الموقع.

## كيف تبدأ ميزة جديدة

عندما يطلب المستخدم ميزة جديدة:
1. شغّل `/speckit.specify [وصف الميزة]` (أو استدعِ `spec-architect`).
2. أكمل سير عمل Spec Kit (clarify → plan → tasks).
3. وزّع المهام على الـ agents المتخصصة.
4. تابع حتى اكتمال الـ Spec والاختبارات.
